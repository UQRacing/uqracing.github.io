2 · Watchdog supervision

watchdog_node runs separately from the stack — mission launchers start the nodes, the watchdog only supervises liveness + topic heartbeats and reports health over CAN. 

flowchart TB

    subgraph MON["Monitored nodes (track-drive)"]

    n1 -.PID.-> pid
    n2 -.PID.-> pid
    n3 -.PID.-> pid
    t1 -->|heartbeat| topics
    t2 -->|heartbeat| topics
    pid --> state
    topics --> state
    state -->|"diagnostics : DiagnosticArray"| ros["ROS 2 graph"]
    state -->|"CAN 0x223 · 500kbit · 8B"| can(["CAN bus"])
    can --> ebs["EBS / ECU
acts on state byte"]
State byteMeaning
0x02All monitored nodes running normally
0x01Some nodes initialised (partial)
0x00All failed / watchdog in FAIL_SAFE → EBS consumes this

CAN frame: arbitration id 0x223 (11-bit), bitrate 500000, DLC 8. No ROS e-stop topic — state is signalled over CAN. Configs: watchdog_track_drive.yaml, watchdog_brake_test.yaml, watchdog_inspection.yaml.

6 · Confidence & gaps

Confirmed (seen in source): Docker compose/Dockerfile/scripts; uqr_ws .repos inventory; watchdog node, config and CAN behaviour; mission launch structure; the topic edges above.

Inferred (dashed): the exact perception→planning→control ordering; that cone_detector ≈ "lidar_processing"; that stack_node wraps detection in the stack monorepo; that 0x00 drives an EBS consumer.

Could not surface (no code-search hits, likely un-indexed private repos): lidar_processing, vape2, glim-stack, stanley_steering, pure-pursuit-trajectory-follower, backup_path_planner, lora_telem; the stack monorepo internals; velocity_compensation / flir_camera_driver_ros2 / lslidar_ros2 internals; acceleration/skidpad/autocross/EBS launch files; dash_debug's full subscription list.
